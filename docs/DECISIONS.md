# Syto — журнал решений

Формат: номер, дата, решение, почему, что это значит. Решения не редактируем задним
числом. Если передумали — новая запись, которая отменяет старую.

## D-001 — Голос проверяем первым (voice-first)

Дата: 2026-09-24. Статус: принято.

**Решение.** Первый прототип — голосовой бот (фаза 1), а не фильтр звонков и SMS.

**Почему.** Приложения «отклонить незнакомого и ответить SMS» уже есть, там нечего
проверять. Голосовой бот — главная идея проекта и одновременно главный платформенный
риск: Android не даёт третьим приложениям доступ к аудиопотоку звонка, часть OEM
блокирует микрофон в режиме разговора. Если это не работает, проект другой.
Узнать это надо до того, как написаны экраны, база и правила.

**Что это значит.** Фаза 1 оптимизирована на скорость получения ответа, а не на
качество кода. Порядок фаз 2–6 фиксируется на гейте G1.

## D-002 — Markdown в `docs/` — единственная точка истины

Дата: 2026-09-24. Статус: принято.

**Решение.** План, статус, решения и результаты экспериментов живут в `docs/*.md`.
Чат и память сессии — не источник. Любая сессия должна стартовать с `CLAUDE.md` → `docs/STATUS.md`.

**Почему.** Сессии теряют контекст. Работа идёт из облака, где нет устройства, а
результаты тестов приходят от пользователя. Без письменной фиксации они теряются.

**Что это значит.** Обновление md — часть каждого шага, а не «потом». Язык `docs/` —
русский (рабочий язык владельца), код и README — английский.

## D-003 — APK доставляем через GitHub Actions

Дата: 2026-09-24. Статус: принято.

**Решение.** Каждый пуш собирает debug-APK в GitHub Actions и выкладывает артефактом.
Пользователь ставит его на телефон. Локальная сборка в Android Studio — опция, не требование.

**Почему.** Облачная сессия не имеет ни устройства, ни гарантированного Android SDK.
Нужен путь «код → телефон», который не зависит от окружения сессии.

**Что это значит.** Фаза 0 не считается готовой, пока APK из CI не запустился на телефоне.

## D-004 — Код спайка может быть грубым

Дата: 2026-09-24. Статус: принято.

**Решение.** В фазе 1 код пишется в модуле `app` в пакете `com.ownnet.syto.voice` без
архитектурных претензий: без Room, без DI, журнал — в файл. В фазе 5 его допустимо
переписать целиком.

**Почему.** Цель фазы 1 — знание, не продукт. Архитектура до ответа «работает ли» —
потерянное время.

**Что это значит.** Ревью кода фазы 1 — по критерию «даёт ли ответ на гипотезу».

## D-006 — Тестовое устройство: realme RMX3999

Дата: 2026-09-24. Статус: принято.

**Решение.** Основной тестовый телефон — realme, модель RMX3999. Версию Android и
realme UI уточнить в настройках телефона и вписать в стенд фазы 1.

**Почему это важно.** realme UI построен на ColorOS (Oppo). Эти прошивки известны
агрессивным управлением фоновыми процессами и аудио, поэтому подфаза 1.3 (микрофон
во время разговора) и удержание `InCallService` живым — зона повышенного риска.
Отключение оптимизации батареи для Syto — обязательный шаг стенда.

**Что это значит.** Второй телефон для тестовых звонков пользователь найдёт.
В README при релизе честно указать, на каком устройстве проверено.

## D-007 — Украинский язык как основной и единственный тренировочный

Дата: 2026-09-24. Статус: принято.

**Решение.** Бот разрабатывается и тестируется на украинском. Русский держим в уме
как возможный второй язык, решение о нём — позже. Английский — после и только если решим.

**Почему.** Для русского и английского решения уже есть (операторы, Google). Для
украинского локального голосового помощника — нет. Это и есть задача проекта.

**Что это значит.** Все тестовые фразы, приветствия, словари ключевых слов и оценка
качества распознавания в фазах 1 и 5 — на украинском. Выбор STT-движка в 1.3
делается по качеству именно украинской модели (Vosk uk, системный офлайн-пакет uk).

## D-008 — Основная разработка локально на Mac, CI как страховка

Дата: 2026-09-24. Статус: принято.

**Решение.** После мержа PR #1 разработка переезжает в локальные сессии на Mac с
Android Studio, Android SDK и adb. Облачные сессии — только для документов и кода
без сборки. D-003 (APK из GitHub Actions) остаётся как страховочный путь и
проверка, что проект собирается «с нуля».

**Почему.** Локально агент может собирать, ставить на телефон по adb, читать logcat
и запускать инструментальные тесты. Это радикально ускоряет фазу 1.

**Что это значит.** Фаза 0 упрощается: 0.1 проверяется локально, 0.2 (CI) остаётся,
0.3 — установка через adb, а инструкция по APK из CI нужна только на случай работы без ноутбука.

## D-009 — Debug keystore лежит в репозитории

Дата: 2026-09-24. Статус: принято.

**Решение.** `app/debug.keystore` (PKCS12, alias `androiddebugkey`, пароли `android`, срок 30 лет)
закоммичен и подключён как `signingConfigs.debug`. `.gitignore` для него сделано исключение.
SHA-256 сертификата: `AD:3A:BA:B8:36:A8:C9:22:EE:B3:A1:18:00:C8:61:B2:44:59:28:89:85:56:DA:CB:96:AE:34:AA:ED:D5:5E:63`.

**Почему.** Android обновляет приложение поверх старого только при совпадении подписи. Сборки
приходят из двух мест — GitHub Actions и Android Studio на Mac (D-008) — и должны ставиться
поверх друг друга. Детерминированно сгенерировать keystore нельзя (ключ случайный); secrets
не доступны локальной сборке и форкам. Debug-ключ не защищает ничего: у стандартного
Android-debug-ключа пароль тоже `android`.

**Что это значит.** Это только debug. Релизный ключ (фаза 6) в репозиторий не попадает никогда —
secrets или локальный keystore. Если keystore когда-нибудь перегенерируется, все установленные
debug-сборки придётся один раз удалить.

## D-010 — На время разработки `versionCode = 1`

Дата: 2026-09-24. Статус: принято.

**Решение.** До фазы 6 `versionCode` не меняется и равен 1. Идентичность сборки — короткий хэш
коммита (`BuildConfig.GIT_SHA`) и номер прогона CI (`BuildConfig.BUILD_NUMBER`), оба на главном экране.

**Почему.** Android не ставит APK с меньшим `versionCode` поверх большего. При смешении CI-сборок
и локальных любой растущий счётчик (номер прогона, число коммитов) рано или поздно даст даунгрейд
и «Приложение не установлено». Одинаковый `versionCode` ставится поверх всегда.

**Что это значит.** Схему версий для релизов решаем в фазе 6. Пока «какая сборка стоит» читаем с экрана.

## D-011 — Сборка на AGP 9 с built-in Kotlin

Дата: 2026-09-24. Статус: принято.

**Решение.** Проект на AGP 9.x. Kotlin компилирует сам AGP (built-in Kotlin); плагин
`org.jetbrains.kotlin.android` к модулям **не применяется**. В корневом `build.gradle.kts` он
объявлен с `apply false` только чтобы зафиксировать версию Kotlin Gradle Plugin на classpath,
и эта версия равна версии `org.jetbrains.kotlin.plugin.compose` (одна запись `kotlin` в
`libs.versions.toml`). `jvmTarget` не задаётся — наследуется от `compileOptions`.

**Почему.** Compose 1.12 (BOM 2026.09) требует AGP 9 и compileSdk 37 — выбора нет. AGP 9 при
попытке применить `kotlin-android` падает. Compose compiler plugin должен совпадать с версией
компилятора Kotlin, иначе сборка не соберётся; фиксация KGP на classpath даёт это совпадение.

**Что это значит.** Рецепты «как в AGP 8» (kotlinOptions, kotlin-android в модуле,
composeOptions.kotlinCompilerExtensionVersion) не применять. Обновление Kotlin — одна строка
`kotlin = "…"` в каталоге, проверяется CI.
